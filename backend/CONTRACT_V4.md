## Intake: POST /api/trial/init

Request: `{request_id, api_version: "1", raw_text, constitution}`. Use RFC 3339
calendar timestamps. Supply one task per nonempty line, at most six; a line is at
most 200 characters. More tasks return 422 instead of silently dropping work.

Response: `{request_id, api_version, source, status: "ok", case, estimated,
questions, relations}`. Source is live or fallback. The calendar is echoed, and
the frontend must show estimates for confirmation before posting /run with
`confirmed: true`. Intake does not create a trial session. Use a fresh request ID
for /run and for every distinct action.

Python keeps the original source line as the task's fact, discarding generated
assertions and deadlines. Relative dates remain in the fact for the user to clarify;
no scheduling deadline is fabricated. In this first version deadline is null even
if the user supplied an explicit date; the confirmation form can supply a precise
deadline. Explicit obligation or task-deadline wording marks mandatory; an exam
alone is context, not an obligation. Maths/studying use category learning. Other tasks default to
reducible. Estimated fields include duration, minimum, buffer, category and flags.

Questions have `{id, task_id, question, options:[{label, fact, patch}]}` and are
capped at three. Option facts remain hypothetical until selected by the user.
The frontend adds the chosen fact to facts and applies the patch before /run.
Patches only contain supplied values, for example `{"buffer_min": 0}`; they never
overwrite other fields with null. Supported patch fields are buffer_min,
duration_min and minimum_min.

Relations have `{a,b,type,reason}`. For depends, **a depends on b** and b is also
written into task a's depends_on. Self references, unknown tasks and cycles are
rejected. Ally/rival do not affect scheduling. The same relations are available
in case.relations so the frontend can retain them when posting /run.

Fallback estimates for the supplied five lines are 120, 60, 30, 120 and 45 minutes,
with a 20-minute gym buffer. Facts remain the user's words. Fallback makes no claim
that these estimates were generated by a model. English and Spanish explicit
integer minute/hour durations override fallback durations.

## Archetypes, natural language and buffers

Generated personas carry archetype and distinct names. Local defaults repair
missing archetypes and generic/duplicate names. Court speeches are prompted to
use natural language, with common schema field leaks also replaced locally.

Task.buffer_min defaults to zero. A scheduled slot begins with that task's buffer,
then approved work, with no gap. Its end includes both. Per-decision original_min
and approved_min describe work. Per-decision saved_min is original work minus
approved work, plus the buffer when the task is DISMISSED. Retained buffers are
not savings. Aggregate original_min, approved_min and pending_min include buffers;
minutes_recovered equals the sum of per-decision saved_min.
A buffer and its task must fit together, obey the deadline, avoid fixed blocks,
and start after dependencies end. A pending or dismissed task reserves no buffer.
For compatibility with the old fixtures, zero buffer fields may be omitted; treat
missing buffer_min as zero. Nonzero schedule buffers are always returned.

The older v4 five-task check now expects 395 requested including overhead, 305
approved including overhead, 90 recovered and 175 free; after the accepted break,
320 approved including overhead, 75 recovered and 160 free.
Its precise slots match Carlos's pasted timetable. These are deterministic engine
checks with prepared recommendations. Temperature zero is used for /run, but
does not guarantee a live model will reproduce those verdicts. Exact pitch numbers
require agreed v4 replay fixtures; v3 replay is still the original 405-minute case.

## Pardon: POST /api/trial/appeal

Add `pardon: true` to the existing request with accepted_replacement omitted/null.
A pardon restores the original title and duration, clears the release and suggested
replacement, rebuilds the plan/calendar, increments revision and fills change.
It never increments appeals_used. Two pardons are enforced per in-memory trial.
Retries with the same request ID are idempotent. A pardon can be used after the
single replacement appeal. If the restored task does not fit it remains PENDING;
restored minutes are not recovered time. Pardon plus replacement is a 422 error.

Pardon is a deterministic user-directed operation, with source fallback and a
specific pardon summary; it does not invoke a model or pretend to be live reasoning.
Use the full returned TrialResult as previous_result for subsequent actions.

## Detailed plan: POST /api/trial/revise

Request: `{request_id, api_version, case, previous_result, base_revision, task_id,
instruction}`. Instruction is detail or free text up to 500 characters.

Response: `{request_id, api_version, source, status: "ok", task_id, first_move,
done_when, action_plan:[{step,minutes,detail,tip}]}`. This supersedes the earlier
full-result revise proposal. The light response never changes the session result,
revision, verdict, approved minutes, calendar, appeal count or other decisions.
The frontend displays it separately. Dismissed tasks must be pardoned or appealed
before requesting a plan. Stale/tampered base results are rejected as on other routes.

The prompt asks for 3–5 specific detailed steps where the minute budget permits.
Python enforces positive integer minutes summing exactly to approved_min; invalid
provider output is retried within the existing time budget, then returns the existing
safe plan labelled fallback. Fallback details explain that expansion is unavailable.

NEBIUS_PLAN_MODEL selects the dedicated model; absent that setting, /revise uses
NEBIUS_MODEL. Gonzalo's local setting now selects zai-org/GLM-5.3-Flash, while /run
stays on Lightning. Full GLM-5.3 repeatedly timed out at 25 seconds, including
with reasoning_effort low; the Flash comparison completed successfully. See
LIVE_VALIDATION.md for the bounded prepared-email checks. Existing provider
timeout/retry bounds remain in force. Failure always returns source fallback,
with model/reason/calls/latency diagnostics in server logs, never provider content.

Plan inference runs outside the session lock. Before returning the result, the
server checks that the base revision and result are still current. A concurrent
appeal or pardon makes the in-flight plan stale and returns 409 rather than
displaying a plan for an obsolete budget. Duplicate request IDs remain idempotent.

## Rules

Optional case.rules: `{mode:"quick"|"standard"|"grand"|"immediate", rounds:1|2|3, severity:0..1, drama:0..1}`.
These settings reach the run prompt. Mode selects frontend pacing and default round count;
explicit rules.rounds takes precedence. Severity/drama
never override facts, mandatory protection, minimums or budget validation.

Travel/setup facts explain buffer time; they are not cited as evidence for reducing
work. A valid judge reduction can still use the authorised minimum, but its reason
states that judgement instead of presenting travel as scope evidence.
